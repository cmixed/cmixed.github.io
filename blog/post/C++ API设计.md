由于向后兼容性要求，制定变更控制流程至关重要。正常的开发过程中，许多开发人员可能会修复 API的错误或向 API添加新功能。其中一些人可能是对良好API设计的各个方面理解得不够全面的初级工程师。因此，在AP1的新版本发布之前，需要一名或多名高级工程师对接口的所有变更进行检查，确定变更是否可接受，是否有正当理由进行修改，以及是否以最佳方式实施向后兼容性。许多开源API还强制执行变更请求流程，只有在获得批准后，才能将变更添加到代码库中。

API往往具有较长的生命周期。开发一个好的API可能需要大量的前期投入，因为要进行额外的规划、设计、版本控制和审查。然而，如果API设计得好，长期成本可能会大大降低，因为你有能力在不干扰客户的情况下对软件进行彻底的更改和提升。即，由于API提供的灵活性，你的开发速度可能会更快。

良好文档对于API的编写至关重要，当你不提供实现的源代码时尤其如此。用户可以通过查看头文件来了解如何使用它，但这并不能定义API的行为，例如可接受的输入值或错误条件。因此，对于任何出色的API来说，编写良好、统一和覆盖全面的文档必不可少。

自动化测试的需求同样非常高。当然，你始终应该测试你的代码。当你实现API时，可能会有数百名其他开发人员和数千名用户依赖于你的实现代码的正确性;因此，如果你正在对API的实现进行重大更改，应当有一套全面的回归测试来保证API行为不会改变，从而确信不会破坏客户的程序。

#### 2.3.4 谨慎添加虚函数 (39)

1. 你可能会对基类进行看似无害的更改，这些更改会对客户产生不利影响。
2. 客户可能会以你从未预期或想象过的方式使用API。
3. 客户可能会以不正确或易出错的方式扩展API。
4. 被覆写的函数可能会破坏类的内部完整性。

除了这些API级别的行为问题，使用CH中的虚函数时，还应注意以下事项。

1. 虚函数调用必须在运行时通过执行虚表(vtable)查找来解析，而非虚函数调用可以在编译时解析。
2. 虚函数的使用会增加对象的大小，增加的通常是指向虚表的指针的大小。
3. 虚函数的添加、重新排序或删除会破坏二进制兼容性。
4. 虚函数并不总是可以内联。
5. 虚函数的重载很麻烦。

如果你仍然决定使用继承，请确保API设计能够安全地支持这一点。记住以下规则。

1. 如果类中有任何虚函数，则始终将析构函数声明为虚函数。这是为了让子类可以释放它们可能分配的任何额外资源。
2. 始终记录类的方法调用彼此的方式。如果客户想为虚函数提供替代实现，需要知道在其实现中需要调用其他哪些方法来保持对象的内部完整性。或者使用线程安全接口之类的设计模式来编写这种依赖关系。
3. 不得在构造函数或析构函数中调用虚函数。这些调用永远不会指向子类(Meyers 2005)。这不会影响API的外观，但这是一个好规则。

**避免将函数声明为可覆写(虚)函数，除非有合理且迫切的需要**。

### 2.5 松耦合 (53)

耦合(coupling)。衡量软件组件之间相互连接强度的指标:每个组件对系统中其他组件的依赖程度。
内聚(cohesion)。衡量单个软件组件的各种功能之间的连贯性或强相关性的指标。

好的软件设计往往与低(或松)耦合和高内聚性相关:一种将不同组件之间的功能相关性和连通性最小化的设计。实现这一目标，可以使组件被独立地使用、理解和维护。

**好的 API 表现出低耦合和高内聚的特性**。

指标评估组件之间的耦合程度：

1. 规模
2. 可见性
3. 关联性
4. 灵活性

### 3.1 pimpl惯用法 (69)

pimpl 意思是 指向实现的指针。

**使用 pimpl 惯用法将实现细节隐藏在公共头文件之外**。

#### 3.1.1 使用pimpl (69)

**使用pimpl惯用法时，优先使用私有嵌套实现类。仅当.cpp中的其他类或自由函数必须访问Impl成员时，才使用公共嵌套Impl类(或公共非嵌套类)**。

1. 只放置私有成员变量。
2. **放置私有成员变量和方法**。
3. 放置公共类的所有方法，使得公共方法只是对Impl类中等效方法的简单封装。

这些选项中的每一个都可能适用于不同的情况，但我推荐选项(2):将所有私有成员变量和私有方法放在Impl类中。这样能够维护对数据及其操作方法的封装，并避免在公共头文件中声明私有方法。

Herb Sutter指出了这种方法的一些注意事项(Sutter，1999)。

1. 无法在实现类中隐藏私有虚函数。它们必须出现在公共类中，以使派生类都可以重载。
2. 可能需要在实现类中添加一个指向公共类的指针，以便Impl类调用公共方法。

#### 3.5.1 模型—视图—控制器 (97)

MVC架构模式要求将业务逻辑(模型)与用户界面(视图)隔离，控制器接收用户输入并协调其他两个部分。

MVC分离支持应用程序功能的模块化，这有以下几个优势：

1. 模型和视图组件的分离使得可以实现多个用户接口，这些接口复用公共的核心业务逻辑。
2. 消除了多个用户界面实现之间底层模型代码的重复。
3. 模型和视图代码的解耦，有助于为核心业务逻辑代码编写单元测试。
4. 组件的模块化允许核心逻辑开发人员和GUI开发人员并行工作，而不会影响彼此。

**MVC架构模式促进了核心业务逻辑(模型)与用户界面(视图)的分离，还将控制器逻辑中影响模型变化的部分和更新视图的部分隔离开来**。

MVC分层设计对代码依赖的核心要求是:视图代码可以调用模型代码(以获取最新状态并更新界面，但反之则不成立:模型代码不应在编译时感知视图代码的存在(因为这会将模型绑定到单个视图)。

## 第4章 设计 (103)

### 4.1 良好的设计 (104)

#### 4.1.1 技术债的积累 (104)

1. 脆弱(Fragility)。当软件出现意外的副作用时，或者当实现细节暴露，导致系统中明显不相关的部分依赖于系统其他部分的内部实现时，软件就会变得脆弱。结果是，对系统某一部分的更改，导致代码中看似无关的部分出现意外故障，所以工程师们害怕接触代码，系统的维护成为负担。
2. 僵化(Rigidity)。僵化的软件很难改变，实际上，设计变得很脆弱，以至于简单的修改也要花费巨大的精力来实现，通常需要大量、耗时和有风险的重构。结果形成了一个糨糊代码库，这大大打击了提交新更改的积极性。
3. 固化(Immobility)。好的工程师会发现代码可以重用的地方，以提高软件的可维护性和稳定性。固化代码不允许进行这种尝试，因此很难在其他地方重用。例如，实现可能与其周围的代码过于纠缠不清，或者工程师可能用某些特定领域的知识进行了硬编码。
4. 专属(Nontransferability)。如果组织中只有一个工程师可以处理代码的某些部分，那么该部分是专属的。通常，责任人是最初编写代码的开发人员，或者是最后一个清理代码的可怜人。对于许多大型代码库，并非每个工程师都能深入理解代码的每一部分。当项目中出现工程师无法轻松理解和有效处理的部分时，那将是一个非常糟糕的情况。

这些问题导致的后果是，组件之间的依赖性增强，代码中概念上无关的部分依赖于彼此的内部实现。随着时间的推移，最终导致大多数程序状态和逻辑变成全局性的或重复性的(见图4.2)。

#### 4.1.2 偿还技术债 (106)

1. 渐进式(Evolution)：设计一个包含所有新需求的系统，迭代重构现有系统，直到解决所有问题。
2. 革命式(Revolution)：扔掉旧代码，从头开始设计和实现一个全新的系统。

两种选择各有利弊，且都困难重重。

#### 4.1.3 长期设计 (107)

1. 一家公司根本不会在一开始就设计出一个好的软件，因为他们认为这将在早期花费宝贵的时间和金钱。
2. 该项目的工程师不懂好的设计技术，或者他们不会把这些技术用于相关项目。
3. 从未打算让代码存在很长时间。例如，为演示而匆忙编写的演示示例，或者是认定会丢弃的原型代码。
4. 软件项目的开发过程不会使技术债越来越明显，随着时间的推移，对需要修复的系统的所有认知都会丢失或遗忘(Scrum 等敏捷流程试图通过使用产品待办事项列表来保持债务的可见性)。
5. 系统最初是精心设计的，但随着时间的推移，由于各种不可控因素，其设计逐渐退化:例如，即使会损害系统的设计，也要将糟糕的更改添加到代码中。用Fred Brooks的话来说，该系统失去了概念的完整性(Brooks，1995)。
6. 不断变更的需求通常也要求设计不断演变，但很多公司有意或无意地持续推迟这项重构工作，而将精力优先放在短期修复、应对黑客攻击和黏合代码上。
7. 错误长期存在。这通常是由于开发者倾向于不断添加新功能，而不关注产品整体质量。
8. 代码未经测试，随着工程师不断修改功能，代码的腐化逐渐深入系统之中，最终导致部分代码库沦为可怕的荒地，让工程师不敢进行修改。

### 4.2 收集功能性需求 (108)

1. 业务需求:从业务角度描述软件的价值(即如何实现组织的需求)。
2. 功能性需求:描述软件的行为(即软件应该完成什么)。
3. 非功能性需求:描述软件必须达到的质量标准(即软件效果如何)。

#### 4.2.1 什么是功能性需求 (108)

1. 用户希望通过API做什么?
2. 从用户的角度来看，最佳的工作流程是怎样的?
3. 可能的输入都有什么?(包括其类型和有效范围)
4. 预期的输出都有什么?(包括其类型、格式和范围)
5. 必须支持哪些文件格式或协议?
6. 用户对问题领域的思维模式(如果有的话)是怎样的?
7. 用户使用什么领域的术语?

如果你正在修改或重构现有的APl，可以要求开发人员评价当前使用API的方式，这有助于了解烦琐的工作流程和 API未使用的部分。你还可以询问他们在理想情况下如何使用API(Stylos等人，2008).

**功能性需求用于指定API的行为**。

功能性需求也可以由非功能性需求支持。非功能性需求定义了API的操作约束。对于用户来说，这些指标与API提供的功能一样重要。非功能性需求的示例包括以下几方面。

1. 性能(performance)。某些操作的速度是否受到限制?
2. 平台兼容性(platform compatibility)。代码必须在哪些平台上运行?
3. 安全性(security)。是否存在数据安全、访问或隐私问题?
4. 可扩展性(scalability)。该系统能否处理实际的数据输入?
5. 灵活性(flexibility)。系统发布后是否需要扩展?
6. 可用性(usability)。用户能否轻松理解、学习和使用API?
7. 并发性(concurrency)。系统是否需要使用多个处理器?
8. 成本(cost)。这个软件要花多少钱?

### 4.3 创建用例 (110)

用例描述了基于用户或另一个软件交互的API行为(Jacobson，1992)。用例本质上是一种功能性需求，用于确定使用API做什么，以及这么做的目的，而非简单地提供一个涵盖特性、行为或实现的说明列表。创建用例时，可以从用户的角度设计API。

通常既要编写功能需求文档，也要编写用例。用例可以从用户的角度描述APl，而功能性需求可以描述功能列表或算法的细节，所以只专注于其中一项就够了。这里建议创建用例，因为这些用例与用户想要与系统交互的方式最接近。使用这两种方法时，可以从用例中导出功能需求，反之亦然。更常规的做法是，首先与用户合作创建用例，然后从这些用例中推导出功能性需求列表。

**用例可从用户角度描述API应满足的需求**。

#### 4.3.2 用例模板 (111)

**用例可以是面向目标的简短描述信息列表，也可以是更为正式的模板定义结构化说明**。

- 名称:用例的唯一标识符，通常采用“动词+名词”格式，如“提取现金”或“购买邮票"
- 版本:用于区分用例不同版本的数字
- 描述:用一两句话概括用例的简短文本。
- 目标:描述用户想要完成什么。
- 参与者:想要实现目标的参与者角色.
- 利益相关者:对用例结果有利益关系的个人或组织(例如ATM用户或银行)。
- 基础流程:描述事件过程的一系列步骤。这应该尽可能避免条件逻辑。
- 扩展:导致采取替代步骤的条件列表，这描述了在目标失败的情况下该怎办（例如，输入了无效的PIN码)。
- 前提条件:触发器成功执行所需的条件列表。
- 触发器:导致用例启动的事件。
- 后置条件:描述成功执行用例后系统的状态。
- 备注:不适合以上类别的附加信息

#### 4.3.3 编写高质量用例 (112)

1. 使用领域术语。
2. 不过度指定用例细节。
3. 用例不必定义所有需求。
4. 用例不定义设计。
5. 不在用例中指定设计。
6. 用例能指导测试。
7. 迭代预期。
8. 适度覆盖。

#### 4.3.4 需求和敏捷开发 (113)

1. 重视个体与互动，而不是流程和工具。
2. 重视可交付的软件，而不是详尽完备的文档。
3. 重视与客户的协作，而不是合同条款的谈判。
4. 重视对变化的响应，而不是严格遵循计划。

敏捷方法论不再强调以文档为中心的流程，而是偏向于迭代工作代码的流程。然而这并不意味着没有文档要求。只是文档要求轻量化了，以便更改。敏捷方法不要求维护个庞大、冗长、正式的需求文档。

**用户故事是一种在敏捷开发过程中，获取用户最小需求的方法**。

用户故事的另一方面是，它们的编写者不是开发人员，而是项目利益相关方：对正在开发的产品感兴趣的用户、供应商、业务所有者或支持人员。保持用户故事简短，让利益相关方能在几分钟内完成。

Mike Cohn建议使用一种简单的格式来描述用户故事(Cohn，2004): `作为一个[角色]，我想要[某物]来[受益]`。

Cohn还提供了一个易于记忆的缩写词来帮助你创建好的用户故事:INVEST。其中每个字母都代表了好的用户故事的一种特性(Cohn，2004):

- 独立性(Independent)
- 可协商(Negotiable)
- 有价值(Valuable)
- 可估算(Estimable)
- 简而精(Small)
- 可测试(Testable)

### 4.4 API的设计要素 (115)

抽象只是对某些东西的简化描述，在不知道如何以编程方式实现的情况下，抽象有助于理解。它倾向于强调该事物的重要特征和职责，而省略了对于理解其基本性质不重要的细节。此外，复杂问题往往体现为具有层级性的抽象结构(Henning，2009)。

复杂系统都有两个重要的层次视图：

1. 对象层次结构:描述不同对象在系统中的协作方式，表示基于对象之间part-of关系的结构化分组(例如，活塞是发动机的一部分，发动机是汽车的一部分)。
2. 类层次结构:描述相关对象之间共享的结构和行为，处理对象属性的泛化和特化。这可认为是对象之间的is-a层次结构(例如，混合动力发动机是一种汽车发动机)。

在设计软件系统时，这两种观点同样重要。

与此相关的是，人们普遍认为软件构建的设计阶段包括以下两项主要活动：

1. 架构设计。描述软件的顶层结构和组织。
2. 详细设计。详细描述设计的各个组件，确保其详细程度足以指导具体实现。

一种通用方法是，先定义一个对象层次结构来描述系统的顶层概念结构(或架构)，再使用类层次结构进行细化。类层次结构为客户端指定了具体的C类。定义API的类之后，也应思考类提供的各个函数和参数。

**API设计包括开发顶层架构和详细的类层次结构。**。

### 4.5 架构设计 (117)

#### 4.5.1 架构开发 (118)

从宏观层面看，为API创建架构的过程可概括为以下四个步骤。

1. 分析影响架构的功能性需求。
2. 识别并考虑架构的约束。
3. 发现系统中的主要对象，并确认它们之间的关系。
4. 沟通并记录架构。

#### 4.5.2 架构的约束 (119)

API并非凭空设计出来的，总会存在影响和约束架构的因素。在设计过程真正开始之前，必须识别并考虑这些因素。这一阶段称为全局分析。其中“全局”一词说明这些因素从整体上影响着系统，作为一个整体，它们往往是相互依存和相互矛盾的。这些因素分为以下三个基本类别。

(1)组织因素，例如:

1. 预算
2. 时间表
3. 团队规模和专业性
4. 软件开发过程
5. 子系统的构建与采购决策
6. 管理重点(如日期、功能和质量)

(2)环境因素，例如:

1. 硬件(如机顶盒或移动设备)
2. 平台(如Windows、Mac 和Linux)
3. 软件约束(如使用其他APD)
4. 客户端/服务器约束(如构建Web服务)
5. 协议约束(如邮件客户端使用的是POP协议还是IMAP协议)
6. 文件格式限制(如必须支持GIF和JPEG图像格式)
7. 数据库依赖(如必须连接到远程数据库)
8. 子系统的暴露与封装决策
9. 开发工具

(3)运行因素，例如:

1. 性能
2. 内存占比
3. 可靠性
4. 可用性
5. 并发性
6. 可定制性
7. 可扩展性
8. 可脚本化
9. 安全性
10. 国际化
11. 网络带宽

软件架构师的工作是优先考虑这些因素，以及功能需求中包含的用户约束，并找到产生灵活、高效设计的最佳折中方案。

**架构设计会受到组织、环境和运营等多方面因素的限制**。

**设计要始终考虑变化，变化是无法避免的**。

#### 4.5.3 识别主要抽象概念 (121)

#### 4.5.4 构建关键对象 (122)

1. 语言。用自然语言来类比，可以发现(一般来说)名词倾向于表示对象，动词代表功能，形容词和所有格名词代表属性(Bourque等人，2004)。可以用第2章中的通讯录API来说明这一点。真实世界中的通讯录和人的对象都是名词，可用来在API中表示关键对象，而将人添加到通讯录或为人添加电话号码等操作是动词，应该表示为对其所修改的对象的函数调用。然而，人名是所有格名词，应作为Person对象的属性，而不是高层次对象本身。
2. 属性。此技术要求对具有相似属性或特征的对象进行分组。这可以使用离散的类别来完成，其中每个对象都是明确的成员或非成员，例如:红色对象与蓝色对象。此技术也可能涉及对象的概率分组，这取决于每个对象与一些模糊的标准或概念的匹配程度，例如:一部电影可归类为动作片或浪漫故事。
3. 行为。此方法根据对象共享的动态行为对对象进行分组。这涉及确定系统中的行为集，并将这些行为分配给系统的不同部分。然后，可以通过识别这些行为的发起者和参与者来推导出对象集。
4. 原型。可为最初识别的对象找到更通用的原型。例如，豆袋椅、吧台凳和躺椅都是椅子的类型，但它们的形式和外观不同。
   可以根据它们在多大程度上展现了原型椅子的功能，对它们进行分类。
5. 域(Shlaer-Mellor 分类法)。Shlaer-Mellor方法首先横向划分系统来创建通用域，然后通过对每个域应用单独的分析来纵向划分这些域。
   这种分而治之方法的好处是，每个域都能形成可重用的概念，可以应用到其他设计问题中。例如，使用之前的ATM示例，域可以是以下之一。
   a. 有形域(tangibledomain)，如ATM或钞票。
   b. 角色域，如ATM用户或银行所有者。
   c. 事件域，如金融交易。
   d. 安全域，如身份验证和加密。
   e. 交互域，如PIN输入或现金提取。
   f. 日志域，用于系统日志信息。
6. 域(neighbors分类法)。James Neighbors将这种术语域的分析作为发现问题域中所有应用程序共享的类和对象的技术。
   该技术通过分析问题域中的相关系统来找到具有共性和独特性的领域，例如:识别所有漏洞跟踩系统中的共同元素或所有谱系程序的一般性特征。
   域(Evans分类法)。与Neighbors的域分析相关的一个课题是领域驱动设计。这是由Eric Evans提出的，旨在使用核心业务概念的演变模型来设计复杂系统。

**识别API的关键对象很难。请尝试从不同的角度看待问题，并不断迭代和完善模型**。

#### 4.5.5 架构模式 (124)

下面对几种更流行的架构模式进行了分类

1. 结构化模式:分层模式、管道模式和过滤器模式，以及黑板模式。
2. 交互式系统:模型一视图一控制器(MVC)模式、模型一视图一表示器模式和表示一抽象一控制模式。
3. 分布式系统:客户端/服务器模式、三层架构模式、点对点模式和代理模式。
4. 自适应系统:微内核模式和反射模式。

即使在一个API中，也可能拥有不同的物理架构层。

1. 与API无关的低级例程，如字符串操作例程、数学函数或线程模型。
2. 实现API主要功能的核心业务逻辑。
3. 允许用户扩展API基本功能的插件API或脚本API。
4. 构建在API核心功能之上的便利API。
5. 用于可视化显示API结果的表示层。

在这种情况下，须对系统的不同架构层施加一个严格的依赖层次结构。否则，层和层之间将发生循环依赖(见图4.7)。这些层中的单个组件也是如此，一般性观点是:架构中较低级别的组件不应依赖于较高级别的组件。例如，核心业务逻辑不能依赖于便利API，否则两者之间将出现循环(如果便利API也向下调用核心业务逻辑)。回顾MVC架构模式，会注意到视图依赖于模型，反之并非如此。这一概念称为无循环层次结构。

**避免AP组件之间的循环依赖关系**。

#### 4.5.6 针对架构的沟通 (126)

一旦软件架构被开发出来，就需要用各种方式进行文档化，这些方式包括简单的绘图或维基页面，或者为架构提供建模符号的各种正式方法，如统一建模语言(UML)或架构描述语言集。

无论采用哪种方法，架构文档都是向工程师传达设计意图的重要形式。可以根据愿景为其实现系统提供更多信息，并确保未来的变更能够继续保持架构的意图和完整性。如果开发团队规模庞大或地理位置分散，这一点尤为重要。

架构文档应包含总体设计的基本原理:考虑了哪些其他设计，权衡了哪些因素，以及最终选定的结构为什么被认定为最优。该原理对于设计的长期维护非常重要，并且可以避免未来的设计师重蹈覆辙。

**在用户文档的附录中描述API的高级架构和设计原理**。

设计还可通过沟通获得同行评审，也能在API发布之前收到反馈并据此改进。事实上在流程早期实施设计审查可以促进架构师、开发人员和客户之间的沟通，有助于生成更全面、更持久的设计。如果API架构师能编写一些验证代码，则可直观地通过实践来传达设计原则。

#### 4.6.3 SOLID原则 (129)

1. S=单一责任原则。这表明一个类的变化应该只有一个原因(即一个对象应该只有一种责任)。
2. 0=开放/关闭原则。这表明对象应该对扩展开放，但对修改关闭(即，可以在不更改其源代码的情况下修改类的行为)。
3. L=里氏替换原则(LSP)。这表示一个对象可以用该对象的子类替换，其行为不会有任何改变。
4. I=接口隔离原则。这表明客户端不应该依赖于它们不使用的接口。从本质上讲，应该将大型单个接口拆分为更小、更具体的接口。这一原则的目标是减少耦合.
5. D-依赖反转原则。这表明客户端应该依赖于抽象，而不是具体的实现。该原则的目标也是通过使软件组件依赖于抽象接口来减少耦合。

#### 4.6.4 使用继承 (129)

通用的设计建议

1. 支持/禁止继承
2. 适当使用继承
3. 避免深度继承
4. 纯虚成员函数可强制子类提供实现
5. 不要向现有接口添加新的纯虚函数
6. 不要过度设计

**避免深度继承层次结构。**

**除非要使用接口或混入类，否则应避免多重继承。**

#### 4.6.5 里氏替换原则 (131)

LSP指出，如果S是T的子类，那么T类型的对象可以被S类型的对象替换，而不会改变行为。

**LSP指出，始终可以在不改变行为的情况下用基类替换派生类。**

#### 4.6.6 开放—封闭原则 (134)

**API应该对不兼容的接口变化关闭，但对其功能的扩展开放。**

#### 4.6.7 迪米特法则 (135)

迪米特法则(Law of Demcter，LoD)，亦称为最小知识原理，是产生松耦合设计的指导方针。

当应用于面向对象的设计时，LoD法则意味着函数可以:

1. 调用同一类中的其他函数。
2. 对同一类的数据成员调用函数。
3. 调用函数所接受的任何参数。
4. 对它创建的任何本地对象调用函数。
5. 对全局对象调用函数(但你永远不应该有全局变量)。

由此推论，永远不应该调用通过一个函数获得的另一个对象的函数。

**LoD规定，只在自己的类中或直接相关的对象上调用函数。**

#### 4.6.8 类命名 (136)

1. 简单的类命名应该功能强大、描述性强且不言自明。此外，应该在建模的问题域中有意义，并且应该以建模的对象(例如，用户、书签或文档)命名。
2. 好名字能推动好的设计。因此，一个类应该做一件事，并且把事做好，类名应该传达其意图(Bloch，2008)。如果一个类很难命名，这通常是设计欠妥的标志。
3. 有时需要使用复合名称来表达更具体、更精确的含义，如TexiStyle.SelecionManagcr或LevelEditor。然而，如果使用的单词超过两个或三个，那么这表明设计太过混乱或太过复杂。
4. 接口和抽象基类使用对象模型中的形容词表示。因此，可以将它们命名为:乱或太过复杂。Renderable、Clonable 或Observable。或者，通常用大写字母“I”作为接口类的前缀。
5. 避免使用含义模糊的缩写。好的类名应该简单明了。不要强迫用户记住缩写的名字和没有缩写的名字。稍后讨论函数命名时，会再次讨论这一点。
6. 应该为顶层符号(如类和自由函数)定义命名空间，这样名称就不会与客户可能使用的其他 API的名称冲突。可以通过C++的namespace关键字或使用短前缀来实现。

### 4.7 函数设计 (137)

#### 4.7.1 函数设计选项 (137)

设计调用函数时，可以控制许多接口选项(Cakos,1996)。首先，对于独立函数，应该考虑以下替代方案:

1. 静态函数还是非静态函数。
2. 按值、按引用还是按指针传递参数。
3. 参数以 const 传递还是以非 const 传递。
4. 是否使用具有默认值的可选参数。
5. 按值、按引用还是按指针返回结果。
6. 返回结果为 const、constexpr、consteval 还是非 const。
7. 使用运算符函数还是非运算符函数。
8. 异常规范的使用。
9. [[noreturn]] 或 [[deprecated]] 等属性的使用。

对于成员函数，应该考虑所有这些独立函数的选项，以及:

1. 虚成员函数还是非虚成员函数。
2. 纯虚成员函数还是非纯虚成员函数。
3. const成员函数还是非const成员函数
4. 将成员函数的访问权限设置为 public、protected 还是 private.
5. 是否为非默认构造函数使用关键字explicit

除了以上这些控制函数逻辑接口的选项，还可为函数指定几个组织属性，例如:

1. 友元函数还是非友元函数
2. 内联函数还是非内联函数

正确应用这些选项，可以对API的质量产生很大影响，应该尽可能地将成员函数声明为const,以表明其不会修改对象。

#### 4.7.4 错误处理 (142)

**使用一致且文档齐全的错误处理机制。**

1. 从 std:.exception中派生出自定义的异常，并定义what(方法来描述故障。
2. 考虑要提供的异常安全级别，下面列出了四种可以提供的异常保证(或Abrahams保证)。
   a. 不抛出保证:确保函数永远不会抛出异常。函数中发生的错误将在内部处理，而不暴露给客户，这也称为故障透明性
   b. 强异常安全:操作失败不会产生副作用，任何原始值都将保持不变。这在语义上称为提交或回滚语义。
   c. 基本异常安全:操作失败可能会产生副作用，但所有不变量都将保留(在抛出错误后，对象仍应包含有效值，并且不会泄漏资源)
   d. 无异常安全:在发生错误的情况下不作任何保证(即数据可能损坏，返回不正确的值，或发生内存泄漏)。
3. 建议使用RAII技术来确保异常安全(确保在抛出异常时资源能被正确清理)。
4. 确保在函数的注释中提供可能引发的所有异常。
5. 你可能倾向于使用异常规范，如throw()说明符，来记录函数可能抛出的异常。但请注意，这些约束将在运行时由编译器强制执行(如果有的话)，并且会影响优化，例如使用内联函数的能力。
6. 为可能遇到的逻辑错误集合创建异常，而不是为每个引发的具体物理错误创建唯一的异常。
7. 如果在自己的代码中处理异常，应该通过引用来捕获异常(如上例所示），而非调用抛出对象的拷贝构造函数。
8. 如果有一个从多个异常基类继承的异常，应该使用虚继承来避免客户代码中的步义和未定义错误，它们可能试图捕获异常。
9. 在Windows 中，异常不能跨越不同运行时的 DLL。任何异常的使用都应该包含在DLL中，并且公共API调用都应该捕获所有异常，并使用不同的技术返回错误，例如错误码或输出参数。

**可从std::exception中派生自定义的异常。**

**在出现故障时，提供准确而完全的诊断细节，并快速、干净利索地引导程序终止。**

## 第5章 风格 (147)

1. 扁平式C API：这是一种可以直接由 C 编译器编译的接口风格。它仅包含一组自由函数以及相应的辅助数据结构和常量。由于这种接口不涉及对象、继承等面向对象特性，因此常被称为扁平式或过程式接口。
2. 面向对象的 C++ API：作为一名 C++ 开发者，你可能非常熟悉这种风格。这涉及具有相关数据和方法的对象的应用，以及继承、封装和多态等的应用。

5. 数据驱动式API：这种类型的接口要求向处理程序发送带名称的命令，其参数封装在灵活的数据结构中，而不是直接调用特定的方法或自由函数。这种风格可很好地映射到支持的网络协议和文件格式中。

### 6.4 模板 (182)

#### 6.4.1 模板术语 (182)

模板是 C++ 标准中经常被理解得不够透彻的一部分，所以让我们从定义一些术语开始，以便拥有一个共同的起点。我将使用下面这个模板声明作为定义的参考：

```cpp
template <typename T>
class Stack
{
public:
    void Push(T val);
    T Pop();
    bool IsEmpty() const;
private:
    std::vector<T> mStack;
};
```

这个类模板描述了一个泛型类 Stack，你可以指定 Stack 中元素的类型 T。

- 模板形参：在模板声明中，模板形参列在关键字 template 之后。例如，在之前的 Stack 示例中，T 是唯一的模板形参。
- 模板实参：模板实参是模板特化时用于替换模板形参的实体。例如，给定一个特化 `Stack<int>`，其中“int”就是模板实参。
- 实例化：编译器通过使用具体类型逐一替换模板的每一个形参来生成常规类、方法或函数。这可以在你基于模板创建对象时隐式发生，也可以在你希望控制代码生成时间时显式发生。
  例如，下面的代码创建了两个特定的 Stack 实例，而编译器通常会为这两种不同类型生成代码：

  ```cpp
  Stack<int>          myIntStack;
  Stack<std::string>  myStringStack;
  ```

- 隐式实例化：这是编译器决定何时为模板实例生成代码的时刻。由编译器决定意味着编译器必须找到一个合适的位置来插入代码，而且它必须确保只有一个代码实例存在，以避免重复符号的链接错误。这是一个重要的问题，可能会导致目标文件的额外膨胀，或者需要更长的编译时间和链接时间。API设计者须知隐式实例化意味着必须在头文件中包含模板定义，这样编译器在需要生成实例化代码时就可以访问这些定义。
- 显式实例化：这是程序员决定编译器应该何时为指定的特化生成代码的时刻。这可以大大提高编译效率和减少链接时间，因为编译器不再需要为所有隐式实例化维护簿记信息。但是，程序员有责任确保指定特化只会被显式实例化一次。从API的角度来看，显式实例化允许将模板实现移到.cpp文件中，从而使用户无法看见它。
- 惰性实例化(lazy instantiation)：这描述的是 C++编译器的标准隐式实例化行为，即它只会为模板中实际使用的部分生成代码。
  例如，针对之前的两个实例化，如果你从未在对象 myStringStack 上调用方法 IsEmpty()，
  那么编译器将不会为该方法的 std::string 特化生成代码。
  这意味着你可以用某种类型实例化模板，而该类型仅适用于类模板的部分方法。
  例如，假设某个方法使用了>=运算符，但是你想要实例化的类型没有定义这个运算符，如果你不调用>=运算符的特定方法，这是没问题的。
- 特化：当模板被实例化时，生成的类、方法或函数被称为特化。更具体地说，这是一种实例化(或生成)的特化。但是，“特化”这个术语也可以用于为某个函数提供具体类型的模板形参并自定义实现的情况。关于API风格的第5章给出了一个示例以展示Stack::Push()方法的整数类型的特化实现。这称为显式特化：

```cpp
template <>
void Stack<int>::Push(int val)
{
    //整数特化的 push 实现
}
```

- 部分特化：这是为模板的一个子集提供特化的情况。即，为模板的一些特性提供了特化实现，但仍然允许用户指定其他特性。例如，如果你的模板接受多个形参，那么你可以通过定义一个只为其中某个参数提供具体类型的特化来实现部分特化。在只有一个模板形参的Stack示例中，你可以为任何类型T的指针特化模板。但是，这仍然允许用户创建任何类型的堆栈，但它也允许你编写特定的逻辑来处理用户创建指针堆栈的情况。这种部分特化的类声明可能如下所示：

```cpp
template <typename T>
class Stack<T *>
{
public:
    void Push(T *val);
    T *Pop();
    bool IsEmpty() const;
private:
    std::vector<T *> mStack;
};
```

### 8.1 通过const引用传递输入参数 (277)

### 8.2 最小化#include依赖 (279)

**根据经验，只有当你在自己的类中使用某个类的对象作为成员变量，或者从该类继承时才需要包含(#include)该类的头文件。**

==注意==:一般来说，更安全的做法是只对自己的代码使用前置声明。通过使用前置声明。你可以将符号的声明方式嵌入你省略的头文件中。
例如，如果你对一个外部头文件使用前置声明，而你的API在该头文件的不同版本的环境中使用，那么该头文件中某个类的声明可能会被更改为 typedef，或者该类可能会被更改为模板类，进而破坏你的前置声明。
这就是你不应该尝试前置声明C+标准库对象的原因之一。例如，始终使用`#include<string>`，而不是尝试前置声明 `std::string`。

**仅前置声明API中的符号。**

**头文件应该包含(#include)或前置声明其所有依赖项。**

### 11.3 文档可用性 (358)

多个研究团队正探究 API 文档的易用性。这项工作包括进行可用性研究，以查看用户在文档中导航和执行特定任务的能力，其宗旨是向 API 设计者提供更好的文档编写方式。下面的列表总结了其中的一些研究结果。

- 索引页面：创建一个总索引页并将其用各个文档元素的知识
- 索引页面：创建一个总索引页并将其用作各个文档元素的起点。这为用户提供了整个文档集的概念地图。此外，每个起点应提供一些指示，说明它将涵盖的内容以及目标用户群体(开发人员、管理人员、法律人员等)。
- 统一风格：API文档通常由不同的元素组成。
- 统一风格：API文档通常由不同的元素组成，有些是自动生成的，有些是手动编写的，还有一些是用户贡献的。你应为所有这些页面使用一致且独特的风格，这样，用户在浏览文档内容时，或者在导航到其他网站时，就能始终保持清醒的认识。
- 代码示例：用户需要阅读的文档通常会很多。考虑到微软开发者网络库的庞大规模，提供示例代码片段和可运行的演示能帮助用户快速理解并应用API。
- 图表：清晰简洁的图表有助于解释高层次概念，对于那些只想快速浏览文档的用户来说，尤其如此。应尽可能使用熟悉的图表格式，例如UML或实体关系图。
- 搜索：好的搜索功能非常重要，能帮助用户尽快找到所需信息。文档的所有部分（包括自动生成的API规范以及任何手动编写的文本）都应可搜索。
- 面包屑导航(breadcrumbs)：使用导航辅助工具，让用户能够跟踪其在文档层次结构中的位置，并轻松返回至上层结构。面包屑一词用于描述将当前所在位置显示为一系列页面并用分隔符（例如，“索引>概述>概念”）分隔的常见技术。此外，应尽量让用户能够轻松回溯到各个高层页面。
- 术语：关键术语的定义和使用应该一致。但是，应避免在不必要的情况下使用专业或深奥的术语，因为这可能会使用户感到困惑和沮丧。

与API可用性相关的一个属性是易学性：一个难用的API很可能也难以学习。
为此，Martin Robillard研究了是什么使得API学习具有挑战性。他发现，学习API的最大障碍之一是支持文档和资源。
例如，他列出了以下这些学习API的障碍(Robillard, 2009)。

- 缺少代码示例：提供的代码示例不足或不充分。
- 内容不完整：文档缺失或呈现不充分。
- 缺少任务重点：没有详细说明如何完成特定任务。
- 缺少设计依据：关于高层架构和设计依据的细节不足或不充分。
- 数据格式不可访问：文档未提供用户所需的格式。

除此之外，许多研究者还关注到开发者往往不愿仔细或深入阅读API文档(Zhong等人，2009)。这表明，提供过多文档有时可能是有害的，因为用户可能会错过真正重要的信息和警告，因为它们被理得太深。使用更高层次的教程和示例代码有助于解决这个问题。

### 12.2 API测试的类型 (371)

1. 开盒测试(open box testing):测试是在了解源代码实现的基础上进行的，通常会使用编程语言自动化测试。
    有时这也被称为白盒测试或透明测试(clear boxtesting)，这意味着测试者可以查看系统的内部工作原理。
2. 闭盒测试(closed box testing):测试是在不了解底层实现的情况下进行的，通常基于功能需求和用例等规范。
    有时这被称为黑盒测试，这意味着其内部工作对测试者来说是不可见的。

- 性能测试(performance testing):验证API功能是否满足最低速度或内存使用要求。
- 负载测试(oadtesting):对系统施加需求或压力，并测量其处理该负载的能力。这通常指的是测试许多并发用户或每秒执行许多API请求。这有时也被称为压力测试
- 扩展性测试(scalability testing):确保系统可以处理大规模的复杂生产数据，而不仅仅是简单测试数据。这有时也称作容量测试或体积测试。
- 浸泡测试(soaktesting):尝试在较长时间内持续运行软件，以使其能够承受持续使用(例如，确保没有重大内存泄漏)并使客户对其稳健性感到满意
- 安全测试(security testing):确保代码满足任何安全要求，例如敏感信息的机密性、身份验证、授权、完整性和可用性
- 并发测试(concurrencytesting):验证代码的多线程行为，以确保其正确运行且不会发生死锁。

**API测试应结合单元测试和集成测试，并根据需要进行性能测试、并发测试和安全测试等非功能性测试。**

#### 12.2.1 单元测试 (372)

**单元测试是一种开盒测试技术，用于验证函数和类在隔离状态下的行为。**

- 固件设置(fixture setup):经典的单元测试方式是在每个单元测试运行之前初始化一个相同的环境或固件，例如，确保依赖对象和单例被初始化，将特定的一组文件复制到己知位置，或用一组准备好的初始数据加载数据库。
这通常在与每个测试相关联的 setUp(函数中完成，以区分测试设置步骤和实际测试操作。相关的tearDown(函数通常用于在测试完成后清理环境。这种方式的一个好处是，相同的固件通常可以被多个测试重用。
- 桩对象/模拟对象(stub/mock object):这种方式通过创建存根或模拟对象来隔离被测试的代码与系统的其余部分，这些对象代替了单元外的任何依赖(Mackinnon等人，2001)。例如，如果单元测试需要与数据库通信，可以创建一个存根数据库对象，该对象接受单元将生成的查询子集，然后返回预设的数据，而不实际连接到数据库。结果是一个完全隔离的测试，不会受到数据库问题、网络问题或文件系统权限的影响。但缺点是创建这些存根对象的过程可能会很烦琐，并且通常不能被其他单元测试重用。另一方面，模拟对象往往更灵活，可以根据个别测试进行定制。

**如果代码依赖不可靠的资源（如数据库、文件系统或网络），应考虑使用框对象或模拟对象来编写健壮的单元测试。**

#### 12.2.2 集成测试 (375)

**集成测试是一种用于验证多个组件之间的交互的闭盒测试技术。**

#### 12.2.3 性能测试 (376)

**对关键用例进行性能测试，有助于避免在不知情的情况下引入速度或内存的退化。**

#### 12.4.2 桩对象和模拟对象 (385)

- 伪对象(Fake Object)：这些对象具有实际功能，但实现更简单，便于测试。例如，在内存中模拟磁盘操作的文件系统。
- 桩对象(Stub Object)：返回预先准备或固定响应的对象。例如，ReadFileAsString()的桩对象会返回一个硬编码的字符串(作为文件内容)，而不是读取磁盘上具名文件的内容。
- 模拟对象(Mock Object)：这些是带有预定义行为的对象，用于验证方法调用的顺序和次数。例如，一个模拟对象可以指定 GetValue()函数在前两次调用时返回10，之后返回20。它还可以验证该函数被调用的次数，例如，仅被调用三次，或至少五次，或者类中的函数以给定顺序被调用。

**桩对象和模拟对象都能返回预设的响应，但模拟对象还会验证其调用行为。**
